| 88 | Loading screen then "frozen": the Dock compact 512 MB JIT pool ran dry (`TAIL REFUSED`, `EXEC ALLOC FAILED`), the game exited (status 700315169), and its last frame stayed on screen because a process that dies never destroys its windows. Its window was 1920x1080 on the 1280x720 desktop, so only the top-left showed under a title bar. | Wine records pool pressure once in `Documents/madeira-pool-pressure.txt` (`[pool-pressure] ml2000`, `MADEIRA_POOL_PRESSURE_MARK=0`); the next app run takes one step more (512 → 896 → 1152) and keeps it as a floor (`MADEIRA_POOL_FEEDBACK=0`). The library says so when the session ends, and names a Windows error exit (`[exit-report] ml2000`, `MADEIRA_EXIT_REPORT=0`). Window layers are keyed by the owning process and retired at its exit (`[winios] ml2000 process exit`, `MADEIRA_WINIOS_EXIT_SWEEP=0`). A Dock session ends once the Dock host and every program it started have exited (`[dock-session] ml2000`, `MADEIRA_DOCK_END_WITH_GAME=0`). A presenting window that does not fit the desktop is aspect-fitted to it, with taps and the arrow mapped into its client pixels (`[desktop-fit] ml2000`, `MADEIRA_DESKTOP_FIT=0`). |
| 87 | Runs; killed by jetsam (~6058/6144 MB) while loading a new area. | D3D11 automatic mip clamp: BC textures ≥1024 px drop their top mip while the process is within 1536 MB of its limit (`[mip-clamp] ml2000`, `d3d11.mipClampAuto=0` / `MADEIRA_MIP_CLAMP_AUTO=0`, `d3d11.mipClampAutoMB`). Wide FEX code-buffer generations are refused under 512 MB headroom. |

| 90 | Same deterministic 32-bit crash (NULL object through the thread's TLS array); cores/x87 made no difference. Crash dumps of 32-bit threads read guest EIP/stack through the WoW64 window and use the 32-bit register map (`[x86_live] ml2000 wow32`, `[rsp-trunc] ml2000 wow32`, `MADEIRA_WOW32_DIAG=0`), plus `[tls-reuse] ml2000`. |
| 89 | Same freeze as log 80: the presenting worker spins at ~100% in user mode while the main thread waits forever on its completion event. The one misaligned lock word (crosses a 16-byte boundary) is updated by two non-atomic emulations at once: LOCK CMPXCHG on the Mach thread (read/compare/write) and LOCK XADD in FEX (two 4-byte CASes, left torn on failure). | Split CASAL from JIT code goes to FEX, so each word has one implementation (`[splitlock] ml2000`, `MADEIRA_SPLITLOCK_FEX=0`); WoW64 defaults `StrictInProcessSplitLocks=1` unless set (`MADEIRA_STRICT_SPLITLOCK=0`); a torn split CAS rolls its upper half back and retries (`MADEIRA_SPLITLOCK_ROLLBACK=0`). D3D9 device lock: `Sleep(1)` back-off after 256 yields (`MADEIRA_D9_LOCK_BACKOFF=0`) and `[d3d9-lock-spin] ml2000` (`MADEIRA_D9_LOCK_DIAG=0`). `[spin-probe] ml2000` samples a hot thread's host/guest PC while a wait is stuck (`MADEIRA_SPIN_PROBE=0`; needs CPU diagnostics, on for Dock sessions). |
| 92 | Not blocked, just very slow: the ml1990 keepbase fix works (no lock timeouts), but Mono's managed heap is PAGE_EXECUTE_READWRITE, so Wine carved it into the JIT pool and every guest store took an emulated store fault (~120-134k/s, the exception thread at ~74% of a core, pool growing 40 MB per 20 s). | In ARM64EC processes, executable anonymous memory without EC_CODE is x64 data to FEX: it stays plain host RW, never enters the pool (`[rwx-data] ml2000`, `MADEIRA_GUEST_RWX_DATA=0` on both Wine and FEX). FEX's own write-protect SMC tracking works on whole 16 KB host pages and upstream's Mono detection disables it as on Windows; the legacy alias assist only runs for image/aliased pages. FEX tracker slots 64 → 512 with stale-slot reclaim (`[xins] ml2000`, `MADEIRA_FEX_TRACKER_WIDE=0`). 32-bit processes and DLL images unchanged. |
