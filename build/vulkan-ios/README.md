# Experimental iOS Vulkan route for Windows x64

This is an opt-in build of Wine's existing Vulkan loader and Unix side against
MoltenVK 1.4.2. The normal build keeps Wine's existing unsupported Vulkan path
and has no new MoltenVK link dependency. No D3D DLL, driver choice, Wine/FEX pin,
feature bit or game-specific check is changed by this source contribution.

The route is experimental and overlaps the approaches in Madeira #88 and #353.
It is offered as a small integration/reference path, not a request to merge
multiple competing Vulkan loaders. Coordinate the preferred architecture before
merging. The Wine submodule stays at the repository's pin; this route does not
require the diagnostic changes in the contributor's private Wine worktree.

## Build

First satisfy `docs/BUILDING.md`, including a configured `wine/build-macos`,
llvm-mingw, the existing native archives, and the SDK required by main. This is
not a replacement bootstrap for those inputs. An SDK lacking
`rusage_info_v6.ri_page_wait_time_mach` still needs the separate portability
change proposed in #399 (or an SDK providing the field).

From the repository root:

```sh
bash build/vulkan-ios/fetch.sh
bash build/vulkan-ios/build.sh
# Build real Wine DLLs AFTER tools/build-stub-dlls.py; that tool overwrites
# vulkan-1.dll with the unsupported stub. Bison 3 is needed for Wine's wrc.
JOBS=2 bash build/wine-pe/build-modules.sh vulkan-1 winevulkan
MADEIRA_MOLTENVK=1 bash build/win32u-unix/build.sh
MADEIRA_MOLTENVK=1 bash build/ntdll-unix/build.sh
xcodebuild -project app/Madeira.xcodeproj -scheme Madeira -configuration Debug \
  -destination 'generic/platform=iOS' -derivedDataPath build/vulkan-ios/DerivedData \
  'MADEIRA_VULKAN_LDFLAGS=-lmadeira_vulkan' \
  CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO CODE_SIGN_IDENTITY= DEVELOPMENT_TEAM= build
```

`fetch.sh` verifies the SHA-256 of the official v1.4.2 `MoltenVK-ios.tar`, then
extracts the headers and static iOS-device archive. `build.sh` compiles the
backend and the pinned Wine Unix thunks, renames only their Unix-table symbols,
and combines them with that archive. It copies the package's Apache-2.0 license
into the app's legal directory. No runtime or DLL binary is committed here.
The backend deliberately contains no local MoltenVK shader/cache policy patches.

`MADEIRA_MOLTENVK=1` is a **native build variable**, not a game config setting.
Both native components must be rebuilt with it and the app must be relinked
with the extra library. To return to a stock build, rebuild both components
without the variable and omit `MADEIRA_VULKAN_LDFLAGS`; restore the original
tracked DLL farm files if the optional PE build replaced them. Do this in a
separate checkout if preserving an experimental build. An ordinary incremental
Xcode build alone does not rebuild these native archives.

The output is an unsigned Debug app; sign it with your own real certificate
and profile. No signing identity is provided or generated by this contribution.
This path targets real arm64 iOS devices, not the iOS simulator.

## Actual call path

```
Windows x64 program / LoadLibraryA("vulkan-1.dll")
  -> Wine vulkan-1 forwarders
  -> ARM64EC WineVulkan PE loader/generated thunks
  -> ntdll's x64-only named WineVulkan Unix table
  -> WineVulkan Unix code / Wine win32u Vulkan core
  -> iOS user-driver (Wine ABI at the pinned revision)
  -> vkCreateMetalSurfaceEXT on a retained real CAMetalLayer
  -> MoltenVK / Metal / iPad GPU
```

Wine owns instance/device/surface/swapchain wrappers. The adapter maps native
Metal surface support to Windows WSI and uses the existing direct/fullscreen
or desktop per-window layers. UIKit work runs through the existing main-queue
bridge. A Vulkan layer's logical bounds remain client pixels while its transform
places it in compositor points; ordinary DXMT layers keep their previous path.
A weak set tracks Vulkan layer identities rather than stale HWND flags.

Presentation support is queried through an actual temporary native Metal
surface, not a constant true. Results, including `VK_SUBOPTIMAL_KHR`, timeouts,
missing entry points and errors, are propagated. Native-required
`VK_KHR_portability_subset` is enabled only when the real driver reports it;
this does not fabricate optional feature bits or expose it as a guest feature.
Wine caches physical-device wrappers after real native enumeration; a later
Windows enumerate call can read that real-device-derived cache.

## Reproduction fixtures

All fixtures are ordinary Windows x64 Vulkan callers. No native Metal call,
fake GPU, game binary, shader dump, Steam credentials or DRM bypass is included.

```sh
TC=toolchains/llvm-mingw-20260421-ucrt-macos-universal/bin
INC=toolchains/moltenvk/MoltenVK/include
mkdir -p build/vulkan-ios/tests
"$TC/x86_64-w64-mingw32-clang" -O2 -Wall -Wextra -Werror -I"$INC" \
  tests/x64/vulkan-smoke.c -o build/vulkan-ios/tests/vulkan-enumerate-x64.exe
"$TC/x86_64-w64-mingw32-clang" -O2 -Wall -Wextra -Werror -I"$INC" \
  -DVULKAN_CLEAR_TEST tests/x64/vulkan-smoke.c \
  -o build/vulkan-ios/tests/vulkan-clear-x64.exe
"$TC/x86_64-w64-mingw32-clang" -O2 -Wall -Wextra -Werror -I"$INC" \
  tests/x64/vulkan-present.c -luser32 -o build/vulkan-ios/tests/vulkan-present-x64.exe
```

Install a build signed with your own certificate, enable JIT, add each EXE to
the library as a 64-bit program, and launch it directly. For one diagnostic run:

```ini
env.WINEDEBUG = err+all,trace+vulkan,trace+loaddll
env.MADEIRA_VK_DIAGNOSTICS = 1
```

Remove trace logging after that run. Backend submit/wait/acquire/present logging
is sampled when requested; native negative results remain errors. `0 FPS` in
the existing winemetal overlay is not a measurement of Vulkan frame submission.
A short fixture can finish between the existing library UI polls and produce a
misleading session-start warning; judge its explicit result and exit code.
That unrelated UI fix is intentionally outside this contribution.

Acceptance:

1. Enumeration: `vkCreateInstance` and count/list enumeration succeed and
   return the real GPU name. Retain native enumeration and Windows-side result.
2. Readback: clear a 16x16 RGBA8 image, copy to mapped memory, wait/invalidate,
   and compare all 1024 bytes. A successful API call alone is insufficient.
3. Present: two sequential HWND/surface/swapchain lifetimes show red, green,
   blue, then red, green, blue, visibly on the iPad. Check both overall and
   per-swapchain results and resource cleanup.

## Validation boundaries and device observations

Earlier broader experimental builds on an Apple M5 iPad passed enumeration,
image readback and two visible RGB rounds. The presentation log recorded 360
presents to `Main Screen`, with `VK_SUBOPTIMAL_KHR` preserved, and exit code 0.
The contributor later reached Detroit: Become Human's game menu and an in-game
scene and confirmed camera control. Those later builds also contained VM,
MoltenVK compatibility/cache and diagnostic changes **not included here**;
the game then failed in a graphics pipeline / queue-submit path.

These observations establish feasibility and help reproduce the path, but are
not exact-revision device verification of this reduced draft. This branch must
be rerun on a real iPad before merge. It does not claim Detroit is fully
compatible or playable, nor that compilation speed/stability has been fixed.
No private raw device logs or game images are published with the source.

The earlier device queried these Vulkan 1.0 core features as false:
`geometryShader`, `logicOp`, `wideLines`, `pipelineStatisticsQuery`,
`shaderStorageImageMultisample`, `shaderCullDistance`, `shaderFloat64`,
`shaderResourceResidency`, `sparseBinding`, `sparseResidencyBuffer`,
`sparseResidencyImage2D`, `sparseResidencyImage3D`, `sparseResidency2Samples`,
`sparseResidency4Samples`, `sparseResidency8Samples`, `sparseResidency16Samples`,
`sparseResidencyAliased`, `inheritedQueries`. Treat this as a device/build
observation, not a feature table guaranteed for every Apple GPU. The fixture
prints actual extensions/features. No complete extension conformance audit,
WoW64 Vulkan, concurrent multiwindow, rotation or full game validation is claimed.
Switching between Vulkan and DXMT on the same still-live HWND/layer has not been
validated; Vulkan ownership currently lasts until that layer is destroyed.

## Host tests

```sh
python3 tests/host/check-vulkan-opt-in.py
python3 tests/host/check-unixlib-binder.py
python3 tests/host/check-vulkan-static.py
python3 tests/host/check-vulkan-surface.py
python3 tests/host/check-vulkan-layer-geometry.py
```

The adapter tests use external API fixtures and do not prove GPU execution.
The geometry check uses real macOS CAMetalLayer objects with external window
lookup fixtures. Surface tests need configured Wine headers; backend tests need
the pinned Vulkan headers. The gate test needs only a C compiler and Bash.
